# 근태 통합관리 — 기존 사이트 확장판

## 적용 범위
기존 Express/PG 세션/근태 달력/직원 관리를 유지하고 월별 마감일, 휴일근무 날짜 및 가능 여부, 직원별 조회 및 CSV 다운로드, 변경 이력 50건 단위 페이지네이션/필터, 감사 이력 6개월 정리 스크립트를 추가했습니다.

## **운영 데이터 보호: 적용 전 반드시 확인**
- 이 ZIP은 **운영 DB에 접속하거나 변경하지 않았습니다.** 실제 Supabase DB와 Render 환경에서의 통합 테스트는 아직 수행되지 않았습니다.
- 기존 DB에 `setup.js`를 **절대 실행하지 마세요**. `schema.sql`은 신규 설치용이고, 기존 DB에는 **`migration.sql`만** 실행합니다.
- 먼저 기존 DB를 별도 안전한 위치에 백업하고 **복원 가능한지 확인**하세요. 업데이트된 `make-backup.js`는 신규 테이블까지 백업하지만, 마이그레이션 이전 DB에는 신규 테이블이 없으므로 **업데이트 전 기존 백업 스크립트 또는 Supabase의 백업 수단**을 이용하세요.
- 가능하면 테스트 DB에서 마이그레이션과 기존 로그인/근태를 검증한 뒤 운영에 적용하세요.
- 마이그레이션을 적용한 다음 GitHub 별도 브랜치에 코드를 올리고, 검증 후 Render 배포하세요. 운영 DB 마이그레이션과 운영 배포는 승인 후 수동으로 진행합니다.

## 기능
- 관리자가 `마감일·휴일 설정`에서 월별 **근태** 및 **휴일근무** 마감일을 각각 설정합니다. 미설정 시 직원의 입력은 차단됩니다. 한국 날짜 기준 마감일 당일까지 입력 가능합니다.
- 관리자가 지정한 날짜만 휴일근무 등록 대상입니다. 주간/야간 네 가지 조합은 `근무 가능 + 야간 가능`, `근무 가능 + 야간 불가`, `근무 불가 + 야간 불가`, `근무 불가 + 야간 가능`으로 저장됩니다. 미등록은 별도로 유지됩니다.
- `직원별 현황`에서 근태·휴일근무 탭, 직원 필터, 휴일근무 매트릭스, Excel에서 열 수 있는 UTF-8 BOM CSV를 제공합니다.
- 관리자 변경 이력은 50건씩 서버에서 조회하며 유형/변경자/기간으로 검색합니다. 이전 감사 기록은 그대로 읽을 수 있습니다.
- 관리자가 사이트에 접속하면 DB 용량을 확인하고, 500MB 무료 한도의 80%인 400MB부터 경고합니다. 확인 실패도 관리자에게 표시합니다. 변경 이력 다운로드 창에서 6개월이 지난 이력의 건수를 확인하고 수동 삭제할 수 있습니다. 삭제 전에 필요한 이력을 내려받으세요. 자동 삭제는 설정하지 않았습니다. DB 한도나 요금제가 바뀌면 경고 기준을 다시 확인해야 합니다.

## 개발 환경 테스트
Node.js 20 이상. `npm ci`, `npm test`, `node --check server.js`, `node --check extra-routes.js`, `node --check public/app.js`.
DB 통합 테스트는 실제 데이터베이스 접속 정보가 필요하며, 이 패키지 제작 환경에서는 수행하지 않았습니다.

## 배포 순서
1. 기존 Supabase DB 전체 백업 및 복원 가능 여부 확인
2. 테스트 DB에서 `migration.sql` 실행 및 기존 계정/기록 검증
3. 운영 Supabase SQL Editor에서 **`migration.sql`만** 실행
4. GitHub에 전체 프로젝트 파일 반영 (특히 `extra-routes.js`, `migration.sql`, `public/*`)
5. Render 기존 서비스 배포 및 로그 확인
6. 관리자 로그인, 직원 로그인, 기존 기록, 마감일, 휴일근무, 현황표, 변경 이력 확인
7. 문제 발생 시 Render 이전 커밋으로 롤백. DB에 추가된 테이블은 **기존 데이터를 보존하므로 무작정 삭제하지 마세요**.

## 운영상 주의
- **기존 가입/재설정 방식은 사번+이름만으로 비밀번호를 설정할 수 있어 계정 선점 위험이 있습니다.** 직원 사용 확대 전 별도의 일회용 초대 코드나 관리자 신원 확인을 구현해야 합니다. 이 패키지는 기존 가입 흐름을 변경하지 않았습니다.
- `PGSSL=disable`은 개발용 로컬 DB에서만 사용하고 운영에서는 인증서 검증을 유지하세요.
- `DATABASE_URL`, `SESSION_SECRET`, DB 인증서는 코드/ZIP/GitHub에 넣지 마세요.
- 휴일근무 등록 내역이 남아 있는 날짜는 데이터 유실 방지를 위해 삭제를 거부합니다.
- CSV는 Excel에서 열 수 있는 형식이며 `.xlsx` 파일은 아닙니다.


## 2026-11 등록 시작일/마감일 개선

- 관리자는 **대상 월의 전월 날짜**로 근태와 휴일근무의 등록 시작일과 마감일을 각각 설정합니다. 예: 2027년 1월 대상이면 2026년 12월 중 시작일과 마감일 선택.
- 일반 직원은 한국시간 기준 시작일 00:00부터 마감일 23:59:59까지만 본인 기록을 생성·수정·삭제할 수 있습니다. 기간 외에는 조회만 가능합니다. 관리자는 예외입니다.
- 시작일이 없는 기존 설정은 안전을 위해 직원 등록을 잠급니다. 관리자가 두 날짜를 다시 저장해야 합니다.
- **이전 수정본 ZIP 대신 이번 ZIP을 사용하세요.** 기존 DB에는 `migration.sql`을 적용해야 합니다. 운영 DB를 초기화하는 `setup.js`는 실행하지 마세요.
- 운영 DB 적용 전 백업 및 마이그레이션 검증이 필요합니다. 이 환경에서는 운영 Supabase 연결 테스트를 수행하지 않았습니다.

## v3 코드 보완 (배포 전 검증 필수)
- 등록 기간 변경과 직원 등록·수정·삭제의 경쟁 상태를 줄이기 위해 대상 월별 PostgreSQL 트랜잭션 advisory lock을 적용했습니다. 동일한 기간 키를 사용하며 여러 달은 정렬된 순서로 잠급니다.
- 근태 수정 시 변경 내용이 전혀 없으면 UPDATE와 감사 로그를 만들지 않고 기존 레코드를 반환합니다.
- 휴일근무의 네 가지 상태는 `status`/`night_status` 조합으로 보존합니다. 미등록은 행이 없는 상태입니다.
- **실제 DB 통합 테스트는 수행되지 않았습니다.** Supabase 운영 DB에 SQL을 실행하기 전에 테스트 DB에서 동시 요청, 권한, 기존 계정, 등록 기간 경계를 확인해야 합니다.
- **가입·비밀번호 재설정의 계정 선점 위험은 아직 해결되지 않았습니다.** 실제 직원 사용 확대 전 별도 보안 개선이 필요합니다.

## 월별 기본 작업장 및 근태 등록 1단계 (작업본)

- 관리자는 `작업장 배치`에서 월별로 직원의 기본 작업장을 지정합니다. 이전 달 불러오기는 현재 월에 미배치된 활성 직원만 추가하며 기존 배치를 덮어쓰지 않습니다. 월별 이력은 서로 독립적입니다.
- 직원은 `근태 등록`에서 자신의 기본 작업장과 등록 기간을 확인하고 기존 근태를 등록하거나, 일정이 없는 경우에만 `이번 달 등록할 일정 없음`을 저장할 수 있습니다. 근태가 등록되면 해당 달의 일정 없음 확인은 해제됩니다.
- 이 단계는 휴일근무·야간 불가능 주간·최종 확인을 포함한 전체 등록 절차가 아닙니다. 공통 등록 기간, 휴일 자동 배치, 지원·조출·야간 편성, 근무표 엑셀은 후속 작업입니다.
- 새 테이블 두 개는 `migration.sql` 마지막에 추가되며 기존 데이터는 삭제하지 않습니다. 기존 운영 DB에 적용하기 전 전체 백업 및 복원 가능 여부를 확인하고, 분리된 테스트 DB에서 SQL과 권한·기존 로그인·근태 변경을 검증하세요. 운영 DB에서 `setup.js`를 실행하지 마세요. 새로운 백업 스크립트는 두 테이블이 생성된 뒤 사용하세요.
